## 1. Docker Images

Docker `Image` is basically a packaged blueprint of a container’s filesystem + instructions on how to run it

`Containers` are lightweight, isolated environments that run your application with everything it needs.<br>

Its like a lightweight isolated running operating system serving process, application and minimal file system. It runs in a host machine

🧠 Simple definition

A `container image` is a read-only package that contains everything needed to run an application:

- application code
- system libraries
- dependencies
- runtime (like Node.js, Python, etc.)
- default startup command

📦 Image vs Container

```sh
IMAGE  = blueprint / template (static, cannot run)
CONTAINER = running instance (live process from image)

# Like:
📦 Image = a recipe book
🍲 Container = the cooked meal

# or

📦 Image = a Windows/Linux ISO file
💻 Container = installed running OS instance
```

A Docker image is comparable to a class, representing a reusable structure that can be instantiated multiple times

Docker Hub is similar to NPM, but for container images instead of code packages

### Docker Images without Docker

First thing, let's go grab a container off of Docker Hub. Let's grab the latest Node.js container that runs Ubuntu.

#### 1. Start a "Docker inside Docker shell"\*\*

```sh
docker run -ti \
  -v /var/run/docker.sock:/var/run/docker.sock \
  --privileged \
  --rm \
  --name docker-host \
  docker:26.0.1-cli
```

**What this means:**

You are starting a container that has Docker CLI inside it.

**Flags explained**:

- `docker run` → start a container
- `-t` → give terminal (TTY)
- `-i` → interactive mode (keep STDIN open)
- `-v` /var/run/docker.sock:/var/run/docker.sock → 🔥 gives container control of HOST Docker engine
- `--privileged` → gives almost root access to the host system
- `--rm` → delete container after exit
- `--name docker-host` → name it “docker-host”
- `docker:26.0.1-cli` → image containing Docker command-line tool

👉 Result:
You now have a shell where Docker commands behave like you're on the host.

#### 2. Run a real container (Alpine Linux)

```sh
docker run --rm -dit --name my-alpine alpine:3.19.1 sh
```

**Meaning:**

You start a tiny Linux container running sh.

**Flags:**

- `--rm` → auto-delete when stopped
- `-d` → run in background (detached)
- `-i` → keep input open
- `-t` → attach terminal
- `--name my-alpine` → name container
- `alpine:3.19.1` → image (small Linux distro)
- `sh` → command to run

📦 Result:

```sh
Container: my-alpine
└── running shell (sh)
```

#### 3. Export the container filesystem

```sh
docker export -o dockercontainer.tar my-alpine
```

**Meaning:**

Take a snapshot of the container’s filesystem.

📦 _You are literally saying:_

“Give me everything inside this container as a tar file.”

Result:

`dockercontainer.tar`

This contains:

- /bin
- /etc
- /usr
- /lib
  etc.

#### 4. Extract it manually

```sh
mkdir container-root
tar xf dockercontainer.tar -C container-root/
```

**Meaning:**

You are rebuilding the Linux filesystem manually.

**Commands:**

- `mkdir container-root` → create folder
- `tar xf` → extract tar file
- `-C container-root/` → extract into that folder

📦 Now you have:

```sh
container-root/
├── bin/
├── etc/
├── usr/
├── lib/
└── ...
```

👉 This is EXACTLY what Docker uses internally as container root filesystem.

#### 5. Create isolated environment (manual container runtime)

```sh
unshare --mount --uts --ipc --net --pid --fork --user --map-root-user \
chroot $PWD/container-root ash
```

🧠 What this command does (simple view)

```sh
BEFORE:
You are inside host system

AFTER:
You are inside isolated mini-Linux # /container-root
```

🧩 **Flags explained**
🧬 Namespace isolation (core container concept)

- `--mount` separate filesystem mounts
- `--uts` separate hostname
- `--ipc` separate shared memory
- `--net` separate network stack
- `--pid` separate process list
- `--fork` create new process inside namespace
- `--user` separate user mapping
- `--map-root-user` make you root inside container

**What `unshare` does**
It says: `“Do NOT share these parts of the OS with the host.”`

**Then `chroot`**
Change root directory to `container-root`

#### 6. Mount required system filesystems

After entering the new environment, run:<br>

```sh
mount -t proc none /proc # Mount process metadata so tools like `ps` work properly.
mount -t sysfs none /sys # Mount kernel and device information.
mount -t tmpfs none /tmp # Provide a temporary in-memory filesystem.
```
