## Cgroups

`cgroups` (short for control groups) is a Linux kernel feature that lets you limit, prioritize, and monitor how much system resources a process (or group of processes) can use.<br>

`grep -c cgroup /proc/mounts` - Checks the cgroup version. v2 is the latest and will print `0`.<br>

`/sys/fs/cgroup/` - Directory where you can read and write configuration files to manage resource limits.<br>

### Get into System Control Group

In Terminal `#2` (the non-unshared one, refer to `3. Namespaces.md`) run:<br>

```sh
cd /sys/fs/cgroup # change directory to system control group
ls # show available cgroup settings files and folders
```

You'll see a bunch of "files" that look like `cpu.max`, `cgroup.procs`, and `memory.high`. Each one represents a setting you can configure for the cgroup.<br>

### Creating a Custom Cgroup

```sh
# create the cgroup
mkdir /sys/fs/cgroup/sandbox

# look at all the files created automatically
ls /sys/fs/cgroup/sandbox
```

Let's move our unshared environment into the custom cgroup. Every process belongs to exactly one cgroup. If you move a process to a cgroup, it is automatically removed from the cgroup it was in. Moving our unshared bash process from the root cgroup to the sandbox cgroup will remove it from the root cgroup without any extra steps.<br>

```sh
# find your isolated bash PID — it's the bash process immediately after the unshare
ps aux

# should see the process in the root cgroup
cat /sys/fs/cgroup/cgroup.procs

# move the unshared env into the sandbox cgroup
echo <PID> > /sys/fs/cgroup/sandbox/cgroup.procs

# should see the process in the sandbox cgroup
cat /sys/fs/cgroup/sandbox/cgroup.procs

# should see the process no longer in the root cgroup — processes belong to exactly one cgroup
cat /sys/fs/cgroup/cgroup.procs
```

We have now moved our unshared bash process into a cgroup. No limits are placed on it yet, but it is there and ready to be managed.<br>

#### What are Controllers?

A controller is a module in the Linux kernel that manages one type of resource for a group of processes.<br>

In cgroups, `controllers` (also called **_subsystems_**) are the parts that actually enforce limits on specific resources. Each controller handles how much of something a group can use.<br>

**Common cgroup controllers:**<br>

1. CPU controller (`cpu`) — limits or prioritizes CPU usage. Example: give a process 20% CPU or lower priority.
2. Memory controller (`memory`) — limits RAM usage and prevents apps from crashing the system. Example: max 512 MB RAM.
3. PIDs controller (`pids`) — limits the number of processes and prevents fork bombs.
4. Block I/O controller (`blkio` / `io`) — controls disk read/write speed. Useful when multiple apps share a disk.
5. CPU set controller (`cpuset`) — pins processes to specific CPU cores. Example: run an app only on cores 0 and 1.
6. Devices controller (`devices`) — controls access to hardware devices. Example: allow or deny access to `/dev/sda`.

```sh
# see all available controllers
cat /sys/fs/cgroup/cgroup.controllers

# sandbox has no controllers yet
cat /sys/fs/cgroup/sandbox/cgroup.controllers

# no controllers are enabled for children yet
cat /sys/fs/cgroup/cgroup.subtree_control
```

#### Preparing a Cgroup to Start Controlling Resources

In cgroups v2, you cannot enable controllers on a group that already has processes inside it.<br>

The flow is:

1. Move processes out
2. Enable controllers
3. Create child groups with limits

```sh
# 1. Create a new group as a parking area for existing processes
mkdir /sys/fs/cgroup/other-procs

# 2. See current processes
cat /sys/fs/cgroup/cgroup.procs

# 3. Move all processes one by one
# Linux requires individual moves; moving a parent may move its children automatically
echo <PID> > /sys/fs/cgroup/other-procs/cgroup.procs

# 4. Verify the root cgroup is empty
cat /sys/fs/cgroup/cgroup.procs

# 5. Enable controllers
# A cgroup can either hold processes or control children — not both
echo "+cpuset +cpu +io +memory +hugetlb +pids +rdma" > /sys/fs/cgroup/cgroup.subtree_control

# 6. Check the sandbox child group
ls /sys/fs/cgroup/sandbox

# 7. See available controllers in the sandbox
cat /sys/fs/cgroup/sandbox/cgroup.controllers
```

**Simple analogy:**<br>

- Root cgroup = main power panel
- Processes = people using electricity
- Controllers = circuit breakers (switches that enforce limits)

**Key takeaway:**<br>

- You must empty a cgroup before enabling controllers on it.
- Controllers are what make cgroups actually limit resources.
- After enabling controllers, child cgroups gain files like `cpu.max` and `memory.max`.
