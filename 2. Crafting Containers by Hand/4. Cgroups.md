## Cgroups

`cgroups` (short for control groups) is a Linux kernel feature that lets you limit, prioritize, and monitor how much system resources a process (or group of processes) can use.

`grep -c cgroup /proc/mounts` - Checks what version of the cgroup, v2 is the latest and it will print 0

`/sys/fs/cgroup/` - directory where you can read and write configuration files to manage resource limits

### Get into System Control Group

In Terminal #2 (the non-unshared one, refer to @3. Namespaces.md) run

```sh
cd /sys/fs/cgroup # change directory to system control group
ls # show list of available cgroup settings files and folders
```
You'll see a bunch of "files" that look like `cpu.max`, `cgroup.procs`, and `memory.high`. Each one of these represents a setting that you can play with with regard to the cgroup.

### Creating custom cgroup

```sh
# creates the cgroup
mkdir /sys/fs/cgroup/sandbox

# look at all the files created automatically
ls /sys/fs/cgroup/sandbox
```

Let's move our unshared environment into the custom cgroup. Every process belongs to exactly one cgroup. If you move a process to a cgroup, it will automatically be removed from the cgroup it was in. If we move our unshared bash process from the root cgroup to the sandbox cgroup, it will be removed from the root cgroup without you doing anything.

```sh
# Find your isolated bash PID, it's the bash one immediately after the unshare
ps aux

# should see the process in the root cgroup
cat /sys/fs/cgroup/cgroup.procs

# puts the unshared env into the cgroup called sandbox
echo <PID> > /sys/fs/cgroup/sandbox/cgroup.procs

# should see the process in the sandbox cgroup
cat /sys/fs/cgroup/sandbox/cgroup.procs

# should see the process no longer in the root cgroup - processes belong to exactly 1 cgroup
cat /sys/fs/cgroup/cgroup.proc
```

We now have moved our unshared bash process into a cgroup. We haven't placed any limits on it yet but it's there, ready to be managed. We have a minor problem at the moment though that we need to solve.

#### What are controllers?

A controller is a module in the Linux kernel that manages one type of resource for a group of processes.

In cgroups, `controllers` (also called ***subsystems***) are the parts that actually enforce limits on specific resources.

Each controller handles how much of something a group can use.

**Common cgroup controllers**
1. CPU controller (`cpu`)
Limits or prioritizes CPU usage
Example: give a process 20% CPU or lower priority
2. Memory controller (`memory`)
Limits RAM usage
Prevents apps from crashing the system
Example: max 512MB RAM
3. PIDs controller (`pids`)
Limits number of processes
Prevents fork bombs (too many processes)
4. Block I/O controller (`blkio / io`)
Controls disk read/write speed
Useful when multiple apps share a disk
5. CPU set controller (`cpuset`)
Pins processes to specific CPU cores
Example: run app only on core 0 and 1
6. Devices controller (`devices`)
Controls access to hardware devices
Example: allow/deny access to /dev/sda

```sh
# should see all the available controllers
cat /sys/fs/cgroup/cgroup.controllers

# there's no controllers
cat /sys/fs/cgroup/sandbox/cgroup.controllers

# there's no controllers enabled its children
cat /sys/fs/cgroup/cgroup.subtree_control
```

#### Preparing a cgroup so it can start controlling resources

In cgroups v2, you can’t enable controllers on a group that already has processes inside it.

So the flow is:

1.Move processes out
2.Enable controllers
3.Now you can create child groups with limits

```sh

# 1. Create a new group for existing processes
# creating a temporary “parking area” for all current processes.
mkdir /sys/fs/cgroup/other-procs

# 2. See current processes
cat /sys/fs/cgroup/cgroup.procs

# 3. Move all processes one by one
# Why one by one?
# - Linux requires it
# - Moving a parent may move its children automatically
echo <PID> > /sys/fs/cgroup/other-procs/cgroup.procs

# 4. Verify root is empty
# Goal: no processes left in root cgroup
cat /sys/fs/cgroup/cgroup.procs

# 🚨 Why all this?
# Because of this rule:
# ❗ “A cgroup can either have processes OR control children — not both.”

# 5. Enable controllers
echo "+cpuset +cpu +io +memory +hugetlb +pids +rdma" > /sys/fs/cgroup/cgroup.subtree_control

# Now you’re turning ON resource controllers for child groups.

# Think:

# +cpu → allow CPU limits
# +memory → allow RAM limits
# etc.

# Before this → child groups can’t control anything
# After this → they can

# 6. Check a child group (sandbox)
ls /sys/fs/cgroup/sandbox

# 7. See available controllers
cat /sys/fs/cgroup/sandbox/cgroup.controllers

Simple analogy
- Root cgroup = main power panel
- Processes = people using electricity
- Controllers = switches
```

**Key takeaway**
- You must empty a cgroup before enabling controllers
- Controllers are what make cgroups actually limit resources
- After enabling → child cgroups get files like:
    cpu.max
    memory.max
