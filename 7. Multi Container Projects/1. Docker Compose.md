## Docker Compose

Is ideal for local development scenarios, spinning up multiple containers, networking them together, and can also handle simple production deployments with up to five container types.

### Before Docker Compose

Imagine you’re building a web app.

Your project might need:

- a Node.js app
- a MongoDB database
- maybe Redis for caching
- maybe another backend service
- Without Docker Compose, you would start each container manually.
  
Example:

```sh
docker run -d --name mongodb mongo
docker run -d --name redis redis
docker run -d --name my-app -p 3000:3000 my-node-app
``` 

Then you must:

- connect them with networks
- remember all commands
- remember ports
- remember volumes
- start them in correct order
  
That becomes annoying quickly.

### What Docker Compose does

Docker Compose lets you define all containers in one **YAML** file.

- Usually the file is called: `docker-compose.yml` or 
- In newer style: `compose.yml`

Inside that file, you describe:

- what containers exist
- which image each uses
- ports
- volumes
- environment variables
- networking
- dependencies

Then instead of running many commands manually, you run:

```sh
docker compose up
```

And Docker starts everything together automatically.

> **`docker-compose`** is **V1** of Docker Compose (a separate binary), while **`docker compose`** is **V2**, where Compose is now a top-level command inside the Docker CLI. Functionally, they are almost the same.


### Real example

Instead of this:

```sh
docker run mongo
docker run redis
docker run my-node-app
``` 
You write this:

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"

  db:
    image: mongo

  cache:
    image: redis
```

Then:

```sh
docker compose up
``` 

Now all 3 containers start together.

### Two scenarios where Docker Compose is particularly useful

1. Local development environments with multiple containers, 
2. CI/CD scenarios like spinning up a mini-cluster for running integration tests
