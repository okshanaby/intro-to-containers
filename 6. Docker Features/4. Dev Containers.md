## Dev Container

A dev container is a Docker container designed specifically for development so every developer gets the exact same ready-to-use coding environment without manually installing everything.

### The Problem Before Dev Containers

Imagine you join a company that uses Ruby on Rails.

To start working, you usually must:

- Install Ruby
- Install the correct Ruby version
- Install Rails
- Install all dependencies
- Configure databases
- Fix missing libraries
- Read outdated setup docs
- Spend hours debugging setup problems

This is frustrating, especially if:

- you’re new to the technology
- your operating system differs
- the docs are old
- the project has many dependencies

Every developer’s computer becomes slightly different.

### The Idea of Dev Containers

Instead of every developer manually setting things up:

The company creates a **Docker container** that already contains:

- Ruby
- Rails
- dependencies
- tools
- database setup
- everything needed

So when you join:

- Open the project
- Open it in a dev container
- Everything works automatically

The container becomes a prebuilt development computer for the project.

### What Happens Technically

The project contains a:

- `Dockerfile`
- `.devcontainer` configuration

These files describe:

- what software to install
- what versions to use
- how the environment should behave

Docker then builds a container with all of that.

### Bind Mounts in Dev Containers

Your actual code still lives on your computer.

Docker uses a **bind mount** to connect:

`Your computer files <-> Container`

So:

- you edit code locally in VS Code
- the container instantly sees the changes

This gives you:

- local editing speed
- container consistency

Best of both worlds.

### What VS Code Does

VS Code has special support for dev containers.

When you open the project, it detects:

`.devcontainer/`

Then it asks:

> “Reopen in Container?”

If you say yes:

- Docker builds the environment
- VS Code connects into the container
- terminal runs inside the container
- extensions run there too

You are basically coding inside Linux even if your host machine is different.

### Example of `.devcontainer`/`devcontainer.json`

```json
// For format details, see https://aka.ms/devcontainer.json. For config options, see the
// README at: https://github.com/devcontainers/templates/tree/main/src/ruby
{
	"name": "Ruby",
	// Or use a Dockerfile or Docker Compose file. More info: https://containers.dev/guide/dockerfile
	"image": "mcr.microsoft.com/devcontainers/ruby:1-3.3-bullseye",
	// Features to add to the dev container. More info: https://containers.dev/features.
	// "features": {},
	// Use 'forwardPorts' to make a list of ports inside the container available locally.
	"forwardPorts": [
		3000
	],
	// Use 'postCreateCommand' to run commands after the container is created.
	"postCreateCommand": "./bin/setup"
	// Configure tool-specific properties.
	// "customizations": {},
	// Uncomment to connect as root instead. More info: https://aka.ms/dev-containers-non-root.
	// "remoteUser": "root"
}
```

Open a Rails project.

Instead of manually installing Rails:

- the container already had Rails installed

Then ran:

```sh
rails server
```

And VS Code automatically:

- starts the server
- forward port 3000
- open the app in browser

Easy.

### Why This Is Powerful

Without containers:

- setup might take 30+ minutes or hours

With dev containers:

- setup becomes almost instant

This is huge for:

- teams
- onboarding
- consistency
- avoiding “works on my machine”
  
### Important Point
**Dev Containers ≠ Production Containers**

They are different.

Dev container:

- Used for coding.

May include:

- editors
- debugging tools
- test tools
- extra packages
  
Production container:

Used to run the final app in production.

Should be:

- smaller
- faster
- more secure
- only contain what’s needed to run

So projects often have:

- one Dockerfile for development
- another for production
  
### Other Tools Besides VS Code

Dev containers started mainly with Microsoft/VS Code, but now many tools support them.

Examples:

- Microsoft VS Code
- JetBrains IntelliJ
- GitHub Codespaces
- DevContainer CLI

So dev containers are becoming a general standard.
