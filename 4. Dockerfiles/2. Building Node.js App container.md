## Building Node.js App container

To move beyond a simple console.log, you’ll create a basic Node.js application that responds to HTTP requests. This is one of the simplest possible web servers and is useful for understanding how apps run inside containers.

### 1. Creating a Simple Node.js Server

```js
const http = require("http");

http
  .createServer(function (request, response) {
    console.log("request received");
    response.end("omg hi", "utf-8");
  })
  .listen(3000);

console.log("server started");
```

This server listens on port **3000** and responds with `"omg hi"` whenever it receives a request.

- Uses Node’s built-in http module
- Listens on port 3000
- Logs requests to the console
- Sends a simple response back to the browser

### 2. Test the App Locally (Important First Step)

Before using Docker, you should confirm the app works on your machine. This ensures any issues later are from Docker—not your code.

Run:

```sh
node index.js
```

Then open: `http://localhost:3000`

-You should see: omg hi
-Terminal should log: request received

### 3. Copy the App into Docker (Using COPY)

To run your app inside a container, Docker needs access to your file. This is done using the COPY instruction in the Dockerfile.

Update your Dockerfile:

```Dockerfile
FROM node:20

COPY index.js index.js

CMD ["node", "index.js"]
```

The COPY instruction moves files from your machine into the container.

- **First `index.js`** → source (your computer)
- **Second `index.js`** → destination (inside container)

### 4. Build and Run the Container

Now you can build and run your container with the updated Dockerfile.

Build:

```sh
docker build -t my-node-app .
```

Run:

```sh
docker run --name node-server --rm my-node-app
```

- `--name` node-server → gives container a name
- `--rm` → deletes container after it stops

At this point:

- The server is running inside Docker
- But you can’t access it yet

### 5. Why You Can’t Access It Yet

Even though the app is running, Docker containers are isolated from your system. That means ports inside the container are not automatically exposed to your computer.

- Your app runs on port **3000** inside container
- Your host (computer) **cannot** see it yet

### 6. Expose the Port (Port Forwarding)

To access the app, you must map the container’s port to your machine using `--publish` (or `-p`).

Run:
```sh
docker run --publish 3000:3000 --rm --name node-server my-node-app
```

Now open: `http://localhost:3000`

How port mapping works:

- `host_port`:`container_port`
- 3000:3000 → same port on both sides

Example:
```sh
docker run -p 8000:3000 my-node-app
# Access via localhost:8000
# Still runs on 3000 inside container
```

### 7. Stopping the Container Properly

You may notice that pressing `CTRL+C` doesn’t stop the container properly. This is because Node.js doesn’t handle certain system signals by default.

To fix this, use the `--init` flag:

```sh
docker run --init -p 3000:3000 --rm --name node-server my-node-app
```

This adds a lightweight process (`tini`) to handle shutdown signals correctly.

- Allows clean shutdown
- Handles signals like SIGINT (`CTRL+C`)
- Recommended for real applications

### 8. Managing Running Containers

If your container is still running and you need to stop it manually:

```sh
docker kill node-server
```

- Stops the container immediately
- Useful if it's running in another terminal

**Key Concepts to Remember**
- Containers are isolated by default
- You must explicitly expose ports
- `COPY` brings your code into the container
- `CMD` defines what runs
- `--init` helps with proper shutdown
