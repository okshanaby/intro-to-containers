## Distroless Containers

Distroless is a minimal container image derived from Debian that has been stripped down to only include what's necessary to run a specific application, with extremely limited functionality and no shell access

This section is about **choosing the right base image for your runtime stage** and why Alpine isn’t always the best option, even though it’s popular.

### 1. Why Alpine can sometimes be problematic

Alpine Linux is small and widely used in containers, but it has one important difference:

- Most Linux distributions use **glibc**
- Alpine uses **musl**

**Why this matters:**
- Some software is built expecting **glibc**
- **musl** behaves slightly differently in rare edge cases

**This can cause:**
- unexpected crashes
- strange bugs
- difficult debugging situations

These issues are **rare**, and many people never encounter them. But at scale (for example, in large systems), they can become painful.

### 2. Alternatives to Alpine

Instead of Alpine, the text suggests four main options:

- **Wolfi** - A modern minimal distro designed specifically for containers
- **Red Hat Universal Base Image Micro** - Enterprise-focused, very small and secure
- **Debian Slim** - Smaller version of Debian but still familiar and stable
- **Google Distroless** - Extremely minimal, focused purely on running apps

### 3. What “Distroless” actually means

“Distroless” doesn’t mean there is no OS at all. It means:

- It is still based on Debian
- But almost everything is removed

What’s missing:

- No package manager (no apt, no apk)
- No shell (no bash/sh)
- No debugging tools

What remains:

- Only what is strictly required to run your app

This makes it:

- Smaller in attack surface
- More secure
- More restrictive

### 4. Understanding the Dockerfile

**Build stage (same idea as before)**

```dockerfile
FROM node:20 AS node-builder
WORKDIR /build
COPY package-lock.json package.json ./
RUN npm ci
COPY . .
```

- Uses full Node.js image
- Installs dependencies
- Prepares the app

**Runtime stage (Distroless)**

```dockerfile
FROM gcr.io/distroless/nodejs20
COPY --from=node-builder --chown=node:node /build /app
WORKDIR /app
CMD ["index.js"]
```

**Key differences:**
- Base image
  - Uses Distroless Node.js image
Node is already built in
- No package installation
  - You cannot run apt or apk
  - Everything must come from the build stage
- Copy from builder
  - Only the built app is copied
  - Keeps runtime clean and minimal

- CMD is different

```dockerfile
CMD ["index.js"]
```
  - You don’t write node index.js
  - The image is already locked to run Node.js
  - It automatically executes your file with Node

### 5. Size vs compatibility trade-off

- Alpine image: ~150MB (small, but uses musl)
- Distroless image: ~175MB (slightly bigger, uses Debian/glibc)

So:

- Distroless is not necessarily smaller
- But it avoids Alpine’s rare compatibility issues

### 6. Security philosophy of Distroless


Distroless images are designed with strict production security in mind:

- No shell → harder for attackers to interact
- No package manager → fewer vulnerabilities
- Only one purpose → run your app

This is why:

- You cannot override the command easily
- You cannot “log into” the container normally

### 7. Practical takeaway

- Alpine is fine for most use cases
- Distroless is better when:
  - you want stricter security
  - you want glibc compatibility
  - you are building production-grade systems
- The main idea remains:
  - Build with a full image
  - Run with a minimal one
